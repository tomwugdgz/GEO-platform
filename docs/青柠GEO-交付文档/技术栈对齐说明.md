# 青柠GEO 技术栈对齐说明

> 本文档用于消解「青柠GEO 交付文档」与「开源仓库 `GEO-platform`（`d:\Mirofish\GEO\`）实际代码」之间的技术栈不一致。
> 结论先行：**概念模型完全一致，后端实现栈不同**——交付文档描述的是产品参考架构（ThinkPHP 8 + MySQL），仓库实际跑的是 FastAPI + PostgreSQL/SQLite + LangGraph + ChromaDB。

---

## 1. 为什么不一致

| 维度 | 青柠GEO 交付文档（参考架构） | 仓库 `GEO-platform` 实际实现 |
| --- | --- | --- |
| 前端 | Vue 3 | Vue 3.5 + Vite 5 + Element Plus（`bmn-frontend/`）✅ 一致 |
| 后端 | ThinkPHP 8（PHP） | **FastAPI（Python）**，`backend/run.py`，端口 5006 |
| 数据库 | MySQL | **PostgreSQL 15 / SQLite**（SQLAlchemy，默认 SQLite） |
| 向量库 | Milvus / Faiss / pgvector | **ChromaDB**（持久化 `backend/chroma_db`） |
| Agent 框架 | 未明确 | **LangGraph + LangChain**（`app/agents/orchestrator.py`） |
| 嵌入模型 | 未明确 | `paraphrase-multilingual-MiniLM-L12-v2`（可选 `BAAI/bge-large-zh-v1.5`） |
| LLM | 多模型 API | Ollama（默认 `qwen2.5:latest`）/ OpenAI / DeepSeek / Qwen / Anthropic |

**根因**：交付文档按产品「目标 / 客户可选部署栈」撰写（PHP 技术栈常见于交付型私有化），而开源仓库是作者基于 Python 技术栈独立实现的版本。两者服务同一套 GEO 方法论，仅实现语言不同。

---

## 2. 概念 → 实际模块映射（六层架构）

交付文档定义的六层逻辑架构，与本仓库代码的一一对应：

| 六层架构 | 交付文档定义 | 本仓库实际模块 | 关键文件 |
| --- | --- | --- | --- |
| **采集层** | Prompt 库 + 多模型 API | 意图 / 监测路由 + 多模型 Adapter + LLM 配置 | `app/api/intent_routes.py`、`app/api/monitor_routes.py`、`app/api/agents.py`、`app/config.py` |
| **执行层** | Agent 并发 → 原始答案 + 引用溯源 → 结构化入库 | 任务 / 服务层 + 诊断流水线 + ORM 入库 | `app/tasks/`、`app/services/`、`app/models/`（SQLAlchemy） |
| **分析层** | 提及提取 / 竞品对比 / 情感（LLM-as-a-Judge） | 诊断 / 竞品逆向 / 多模态路由 | `app/api/diagnosis_routes.py`（AIVO 四维）、`app/api/competitor_routes.py`（6 维逆向）、`app/api/multimodal_routes.py`（BVI） |
| **知识资产** | 知识库 → 切片 → Embedding → 向量库 | 知识库路由 + ChromaDB + sentence-transformers | `app/api/knowledge_routes.py`、`backend/chroma_db` |
| **优化层** | EEAT 评分 / Schema / llms.txt 校验 / 结构修复清单 | 优化 / 内容生产路由 | `app/api/optimization_routes.py`、`app/api/content_routes.py`（GEO/SEO 双优化生成） |
| **展示层** | 仪表盘（可见度 / 引用率 / SoV / 情感）+ 归因报告 | 前端 SPA + 看板 / 报告导出 | `bmn-frontend/`、`app/api/monitor_routes.py`（`/board`）、`reportlab`/`python-docx` 报告生成 |

> 蒸馏词工作流 = 采集层（Prompt 库 / 意图）→ 执行层（监测）→ 分析层（提及提取）→ 优化层（EEAT / 结构修复）→ 展示层（报告），全链路在 `app/api/*` 路由中闭环。

## 3. 仓库内需清理的遗留文件（偏差项）

以下文件是从同作者的 **AIAdPlacer / pDOOH** 项目复制而来，与 GEO 不匹配，**不影响源码直接运行，但容器化部署前必须处理**：

| 文件 | 问题 | 建议 |
| --- | --- | --- |
| `docker-compose.yml`（仓库根） | 引用 `ai_adplacer` 库、端口 5002、`TENCENT_MAP_KEY`，且 `backend/Dockerfile` / `frontend/Dockerfile` 不存在 | 重新生成 GEO 专用编排（端口 5006 + 5173） |
| `.env.example`（仓库根） | AIAdPlacer 模板（`ai_adplacer` / 腾讯地图） | 替换为 GEO 配置（`DATABASE_URL` / `LLM_PROVIDER` / `CHROMA_PERSIST_DIR`） |
| `backend/.env.example` | 仍含 `pdooh.db` / `MCP_SERVER_PORT=5002` 等 pDOOH 残留 | 清理为 GEO 变量，默认 `sqlite:///./geo.db` |
